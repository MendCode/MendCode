Create, preview, save, start, inspect, pause, resume, stop, delete, or retry a first-class MendCode Workflow.

Use this tool for one-shot declarative work with explicit phases, dependencies, parallel tasks, validation, or a final synthesis. Use task instead when one independent agent call is enough. A workflow runs independently from a loop; do not create a loop when the user only asked for one workflow run.

Build a valid plan with this checklist:
- Use formatVersion: 1 and unique, stable IDs for every phase and task.
- Every phase lists its task IDs and every task points back to that phase.
- Every task includes dependsOn. Use [] for entry tasks; use producer task IDs for dependent tasks.
- If a task consumes another task's output through inputs, it must depend on that producer directly or transitively.
- finalTaskID must name a synthesize task with a non-none output.
- Define at least one concrete completion criterion.
- Keep requiredGates empty for immediate execution. This tool cannot approve unresolved gates.
- Omit budget unless the user requested limits. If supplied, maxFanOut must cover the total bounded task/map fan-out and maxConcurrency must be positive.
- Model precedence is task.model, then plan.model, then the task agent's configured model, then MendCode's global default model. Set plan.model to pin the whole workflow or task.model for one task; otherwise omit both so global config remains authoritative.
- Use permissions and workspace deliberately. Report-only workflows cannot enable edits or mutating commands.

For a new immediate workflow, follow exactly this sequence:
1. Call preview once with the complete plan. Preview validates only and never creates a run.
2. If preview succeeds, call start once with the exact same plan. Do not omit the plan from start unless you are starting a saved revision or definition.
3. After start succeeds, return control to the user. Do not poll, sleep, wait, or repeatedly call show; the durable runner and workflow monitor report progress.

When validation rejects a plan, correct the reported fields and preview the complete corrected plan again. Do not start a plan that has not passed preview. Prefer saved immutable revisions or definitions when one already exists. Workflow snapshots are bounded; inspect artifacts and events explicitly instead of requesting unbounded child transcripts.

Use concise, action-oriented display names. Phase names describe stages and task names describe actions; never reuse the exact same name for a phase and one of its tasks.

For `originSessionID`, omit it or use `current` to attach the workflow to the current session; do not invent a placeholder session ID.

Delete only when the user explicitly asks. A workflow must be completed, failed, or stopped before it can be deleted.
